# قاعدة العمل المستمر — مرصد السعودية
**الرمز التشغيلي:** قع  
**الإصدار:** 1.0  
**تاريخ الاعتماد:** 22 نوفمبر 2026

عندما يسبق الرمز **قع** أمر المستخدم، فهذا يعني تنفيذ الطلب وفق هذه القاعدة والخطة الرئيسية في docs/MASTER_PRODUCT_PLAN.md.

## 1. الاستمرارية
- ابدأ من آخر حالة فعلية في GitHub والفرع والـPR والاختبارات والنشر، لا من ملخص قديم وحده.
- لا تنشئ مشروعاً أو مستودعاً جديداً؛ استخدم amer88ag/marsed-sa.
- لا تكرر عملاً منجزاً، ولا تفترض أن الملف أو الميزة موجودة دون فحص.
- اعتبر «اكمل» و«نفذ» توجيهاً للاستمرار إلى الخطوة العملية التالية متى كانت آمنة ومحددة.

## 2. ترتيب الأولويات
1. سلامة المشروع وعدم إفساد الحالة القائمة.
2. تدقيق المستودع والفروع وPRs وحالة النشر.
3. الأمن والخصوصية والصلاحيات والأسرار.
4. صحة مصادر البيانات والتراخيص وجودة البيانات.
5. سلامة المعمارية والعقود والخدمات.
6. ربط الواجهة بالخدمات ومصادرها.
7. إكمال وظائف المستخدم ذات الأولوية.
8. اختبارات الوحدات والتكامل والواجهة والأداء.
9. تحسين تجربة المستخدم وإمكانية الوصول.
10. التوثيق وحالة التنفيذ والإصدار.

## 3. طريقة تنفيذ كل مهمة
- افحص الملفات والاعتماديات ذات الصلة قبل التعديل.
- حدد أثر التغيير على الواجهة والخدمة والمزود والسجل والاختبارات.
- نفذ في فرع مستقل واضح الاسم، ولا تعدل main مباشرة.
- حافظ على التغييرات السابقة، ولا تستبدل ملفات كاملة دون مراجعتها.
- أضف اختبارات مناسبة، وشغّل الاختبارات المتاحة وسير CI.
- افحص النتيجة الفعلية بعد التعديل، ولا تكتفِ بنجاح كتابة الملف.
- حدّث الوثائق وحالة التنفيذ بعد إنجاز يمكن إثباته.

## 4. صلاحيات التنفيذ
- يجوز تنفيذ الفحص والتوثيق والتعديلات الروتينية والاختبارات وإنشاء فرع وفتح PR دون طلب إذن لكل خطوة.
- **ممنوع الدمج إلى main أو النشر الإنتاجي أو تغيير إعدادات الإنتاج أو حذف بيانات/فروع أو تدوير أسرار دون موافقة صريحة.**
- لا توصف مهمة بأنها منشورة أو مدمجة ما لم يثبت ذلك من الحالة الفعلية.
- لا تدّع نجاح اختبار أو تغطية أو توفر مصدر دون نتيجة موثقة.

## 5. قواعد البيانات والمصادر
- لا تنشئ قاعدة بيانات مبكراً؛ لا تضفها إلا عند وجود احتياج وظيفي وأمن واضح.
- لا تضع مفاتيح أو أسرار في ملفات الواجهة أو المستودع.
- لا تحول null إلى صفر، ولا تخلط الرصد بالتوقع أو التقدير.
- افصل المنتجات المختلفة ومصادرها ومنهجياتها، واظهر المصدر والتوقيت والوحدة والدقة والقيود.
- لا تطلق تنبيهات سيول/سلامة دون مصدر رسمي أو نموذج متحقق منه ومراجعة مناسبة.

## 6. التقارير للمستخدم
بعد كل دفعة عمل، اذكر بوضوح:
1. الحالة التي فُحصت (فرع/commit/PR).
2. ما الذي تغير والملفات المتأثرة.
3. الاختبارات التي شغلت ونتائجها الفعلية.
4. ما بقي أو فشل أو يحتاج اعتماداً.
5. الخطوة التالية المحددة.
استخدم روابط مباشرة للفروع والـPRs والـActions عند توفرها، وميّز بين المنجز والمقترح والمعلق.

## 7. الاستقلالية دون تجاوز
لا تسأل المستخدم عن تفاصيل سبق أن حسمها أو يمكن فحصها من المستودع. اسأل فقط عند وجود قرار منتج أو قانوني أو مالي أو إنتاجي لا يمكن اتخاذه بأمان من الأدلة المتاحة. نفّذ كل ما هو واضح وآمن قبل السؤال.
