# الهيكل التنظيمي المستهدف — مرصد السعودية

> هذه وثيقة تنظيمية ملزمة للتوسع التدريجي. لا تعني نقل الملفات الحالية دفعة واحدة، ولا تغيير إطار العمل أو إضافة خدمات مدفوعة. الوضع الحالي صفحة HTML واحدة مع أدوات Python وملفات بيانات؛ لذلك يكون الانتقال مرحلياً مع بقاء النسخة العاملة قابلة للاختبار في كل خطوة.

## 1. مبادئ البنية

1. **فصل المسؤوليات:** العرض لا ينزّل البيانات ولا يحلل GeoTIFF؛ ومهام الاستخراج لا تعتمد على عناصر الواجهة.
2. **مصدر حقيقة واحد:** تعريف المدن والمصادر والمنتجات والوحدات والمخططات في موضع موثق، مع تجنب نسخ التعريفات في ملفات متعددة.
3. **العزل حسب المجال:** الطقس، الأمطار، الخرائط، وكتالوج البيانات مجالات مستقلة تتواصل عبر عقود واضحة.
4. **قابلية التحقق:** كل مصدر له محول مستقل واختبارات بيانات وعقد، وكل طبقة تعرض مصدرها ومنهجيتها وتاريخها.
5. **الأمان أولاً:** لا أسرار في المتصفح أو Git؛ التحقق من المدخلات والملفات قبل اعتمادها.
6. **الاقتصاد:** لا قاعدة بيانات أو خادم أو إطار عمل جديد قبل إثبات الحاجة والتكلفة.
7. **التدرج:** لا نقل جماعي ولا إعادة كتابة شاملة؛ كل خطوة صغيرة، قابلة للرجوع، وتمر عبر CI.

## 3. حدود المسؤوليات والعقود

| الطبقة | مسؤوليتها | ممنوع عليها |
|---|---|---|
| واجهة التطبيق | عرض الخرائط والرسوم وحالة البيانات | تنزيل GeoTIFF أو تخزين مفاتيح سرية |
| مجالات التطبيق | منطق اختيار المدينة والمنتج والفترة | معرفة تفاصيل HTTP أو مزود التخزين |
| كتالوج البيانات | تعريف المصدر والترخيص والدقة والوحدات والتأخر | افتراض صلاحية الترخيص أو إخفاء القيود |
| محولات الخدمات | الاتصال بالمزود وتوحيد الاستجابة | تغيير معنى القيم أو اختلاق بيانات عند الفشل |
| خطوط المعالجة | التنزيل والتحويل والفحص وإنتاج ملفات موثقة | تعديل الواجهة أو تجاوز فحوص الجودة |
| البيانات الناتجة | ملفات ذات مخطط وإصدار وبصمة ومصدر | بيانات مجهولة المصدر أو غير قابلة لإعادة الإنتاج |
| الاختبارات | التحقق من العقود والسلوك والجودة | الاعتماد على اتصال حي في كل اختبار وحدوي |

**عقد كل طبقة بيانات:** `id`, `title`, `provider`, `product`, `product_version`, `license`, `attribution`, `units`, `spatial_resolution`, `temporal_resolution`, `coverage`, `timestamp`, `method`, `limitations`, `quality_status`.

لا تُعرض طبقة دون إظهار أهم حقول المصدر والمنهجية والقيود للمستخدم.

## 4. تنظيم تدفق البيانات

```text
مصدر خارجي
   ↓
فحص المصدر والترخيص والمنتج
   ↓
محول خاص بالمصدر
   ↓
ملف خام مؤقت (خارج Git إذا كان كبيراً أو غير مسموح بإعادة توزيعه)
   ↓
التحقق من الملف والقيم والإحداثيات والتواريخ
   ↓
تحويل موحد بوحدات موثقة
   ↓
ملف ناتج + manifest + بصمة
   ↓
اختبار العقد والجودة
   ↓
كتالوج الطبقات
   ↓
واجهة الخريطة والرسوم
```

عند فشل المصدر: تظهر حالة عدم توفر واضحة ووقت آخر تحديث؛ لا تستبدل القيم المفقودة بأصفار ولا تستعمل بيانات قديمة وكأنها حديثة.

## 5. استراتيجية الاختبارات والجودة

- **Unit:** حسابات الوحدات والتواريخ والتحويلات والتحقق من القيم.
- **Contract:** تطابق JSON مع المخطط، الحقول الإلزامية، إصدار المخطط، تعريف المدن والمنتجات.
- **Integration:** محول كل مصدر وخط المعالجة باستخدام fixtures ثابتة.
- **Live smoke:** اختبار حي محدود ومجدول أو يدوي، لا يكون شرطاً لكل اختبار وحدوي.
- **UI:** حالات التحميل والفراغ والخطأ والبيانات القديمة والجوال وإمكانية الوصول.
- **Security:** منع الأسرار، فحص التبعيات، والتحقق من مدخلات الملفات والروابط.

لا يعتمد أي تغيير بيانات أو محول قبل نجاح الاختبارات الثابتة؛ وفشل المصدر الحي يسجل منفصلاً عن فشل منطق التطبيق.

## 6. الحوكمة وسير العمل

- الفروع: `main` للإصدار المعتمد، وفروع قصيرة باسم المجال مثل `feature/precipitation-contracts`.
- كل PR يشرح الهدف والنطاق والملفات المتأثرة والاختبارات ومخاطر البيانات والترخيص.
- لا دمج قبل نجاح CI ومراجعة الفروق وموافقة صاحب المشروع.
- لا نشر تلقائي من فرع البحث. النشر من `main` فقط بعد اعتماد صريح.
- التغييرات في المخططات مصحوبة برقم إصدار وخطة توافق؛ لا يكسر ملف البيانات بصمت.
- القرارات المعمارية الكبيرة تسجل في `docs/decisions/ADR-NNN-*.md`.

## 7. خطة الانتقال من الوضع الحالي

| المرحلة | العمل | شرط الإكمال |
|---|---|---|
| A — توثيق | اعتماد هذه البنية وتحديد الوضع الحالي | لا تغيير سلوكي؛ الوثائق متسقة |
| B — عقود البيانات | نقل تعريف المدن ومخطط CHIRPS إلى ملفات domain قابلة للاختبار | لا اختلاف في البيانات المعروضة |
| C — فصل المعالجة | تنظيم أدوات CHIRPS تحت pipelines مع إبقاء واجهات CLI متوافقة | اختبارات Python وCI ناجحة |
| D — فصل الواجهة | استخراج CSS وJS من index.html إلى src/shared وsrc/features تدريجياً | تطابق بصري ووظيفي واختبارات UI |
| E — محولات المصادر | فصل Open-Meteo وCHIRPS وIMERG بمحول مستقل | تبديل المصدر دون تعديل مكونات العرض |
| F — إصدار مستقر | إضافة فحوص أمان وأداء وإمكانية وصول ومراجعة الترخيص | بوابة إصدار مكتملة وموافقة صريحة |

## 8. ما لا ننفذه الآن

- لا نضيف React/Vue أو TypeScript أو bundler قبل تقييم الحاجة؛ الصفحة الحالية لا تملك package.json.
- لا نضيف PostGIS أو قاعدة بيانات أو API خلفية ما دامت الملفات الثابتة تفي بالغرض.
- لا نضع بيانات GEOSA أو حدوداً إدارية غير مرخصة.
- لا نبني خرائط تدرج مكاني من 13 نقطة مدينة.
- لا ندعي التنبؤ بالسيول أو الرصد الرسمي أو التحقق الميداني.
- لا نحذف ملفات أو نغير مسارات قائمة قبل حصر الاستدعاءات والاختبارات.



## 10. التوسع إلى منصة خدمات ومصادر متعددة

الهيكل لا يقتصر على خدمات الطقس والأمطار. يجب أن يسمح بإضافة خدمات من مواقع وجهات متعددة دون ربط الواجهة مباشرة بكل موقع. نعتمد الفصل التالي:

- **Service:** ميزة المستخدم مثل الطقس أو الأمطار أو جودة الهواء أو الزلازل أو المياه أو التقارير.
- **Provider:** الموقع أو الجهة المالكة للبيانات.
- **Connector/Adapter:** وحدة مستقلة تتصل بالمزود وتحوّل الاستجابة إلى عقد المرصد.
- **Registry:** سجل يربط الخدمات بالمزودين والمنتجات والتراخيص والحالة.

يمكن للخدمة الواحدة استخدام عدة مزودين، ويمكن للمزود الواحد تغذية عدة خدمات. ولا يعني اختلاف المزود إنشاء واجهة خدمة جديدة بالضرورة.

### عقد الخدمة والمزود

كل خدمة تسجل معرفاً ثابتاً، ووصفاً، وفئة، ونقطة تحميل، وقدراتها، والمزودين المدعومين، وحالتها. وكل مزود يسجل معرفه، والرابط الرسمي، والمنتجات، ونوع المصادقة، وحدود الطلب، والتغطية، والترخيص، والإسناد، وحالة التشغيل.

كل استجابة موحدة تحفظ `schema_version`, `service_id`, `provider_id`, `product_id`, وقت الجلب، ووقت صلاحية/رصد البيانات، والموقع، والقيمة والوحدة، ومؤشرات الجودة، ورابط المصدر، والترخيص، والمنهجية والقيود.

### قواعد التعدد والاعتمادية

- تعطل مزود واحد لا يعطل بقية الخدمات.
- المصدر البديل لا يستخدم بصمت إذا اختلفت دقته أو منهجيته؛ يجب إظهار التحول للمستخدم.
- احترام حدود الطلب و`Retry-After`، وإعادة المحاولة المحدودة.
- تخزين مؤقت بمدة صلاحية مختلفة حسب طبيعة المنتج، وعدم عرض بيانات قديمة كأنها حديثة.
- لا تحويل للقيم المفقودة إلى صفر.
- لا أسرار في المتصفح أو المستودع؛ مفاتيح API لا تستخدم إلا في بيئة خادم آمنة عند الحاجة.
- كل مصدر يمر بمراجعة حقوق الاستخدام والعرض العام والإسناد قبل التفعيل.

### بوابة إضافة مصدر جديد

1. تحديد هل المطلوب خدمة جديدة أم مزود إضافي لخدمة موجودة.
2. توثيق الجهة والرابط الرسمي والمنتج والترخيص وحق العرض والتغطية والدقة والتأخر والوحدات والتكلفة والمصادقة.
3. إنشاء موصل مستقل لا يعرف تفاصيل الواجهة.
4. تحويل البيانات إلى العقد الموحد دون تغيير معناها.
5. إضافة عينات اختبار ثابتة واختبارات أخطاء المصادقة وحدود الطلب والبيانات الناقصة.
6. تسجيل المزود والمنتج في الكتالوج وربطه بالخدمة.
7. تفعيل المصدر بعد نجاح اختبارات البيانات والأمان والترخيص.

التفاصيل والنموذج وقائمة قبول PR في [SERVICE_INTEGRATION_GUIDE.md](./SERVICE_INTEGRATION_GUIDE.md).

### التنفيذ المرحلي

لا تُنشأ جميع المجلدات أو تُنقل الملفات دفعة واحدة. يبدأ التنفيذ بسجل خدمات ومزودين وعقود قابلة للاختبار، ثم فصل CHIRPS وOpen-Meteo كموصلين مرجعيين، ثم فصل واجهتي الطقس والأمطار، وبعدها تضاف خدمات جديدة. تبقى `index.html` وملفات Python الحالية عاملة حتى يثبت البديل بالاختبارات.

## 11. تعريف الجاهزية المعمارية

تكون البنية جاهزة للتوسع عندما تكون مسؤولية كل وحدة واضحة، وعقود البيانات موثقة، ومصدر كل طبقة قابلاً للتتبع، والاختبارات تغطي الوحدات والتكامل، ويمكن استبدال مزود دون إعادة كتابة الواجهة، ويمكن بناء المشروع وتشغيله دون أسرار أو خدمات مدفوعة إلزامية.
